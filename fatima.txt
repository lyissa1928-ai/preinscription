# Architecture du projet Gestion Scolaire

## 1. Vue d’ensemble

- **Backend** : NestJS, Prisma, base SQLite (dev) / PostgreSQL (prod).
- **Frontend** : Next.js 16 (App Router), React, Tailwind.
- **Communication** : REST API, JWT dans `Authorization: Bearer`, URL backend via `NEXT_PUBLIC_API_URL` (défaut `http://localhost:3000`).

### 1.1 Contexte environnement

Le projet est actuellement en **phase de test et de développement**.

Il n'y a **pas encore de nom de domaine public**.

Environnement actuel :

- Backend : localhost
- Frontend : localhost
- Base de données : SQLite (dev)
- Accès : réseau local

Règles importantes :

- ne pas hardcoder d'URL publique
- toutes les URLs doivent utiliser des variables d'environnement
- API backend configurable via `NEXT_PUBLIC_API_URL`
- CORS configuré pour localhost et réseau local
- Swagger accessible en local
- aucune dépendance à un nom de domaine public

Prévoir simplement une architecture compatible avec une future production.

## 2. Backend (NestJS)

### 2.1 Configuration

- **Port** : `process.env.PORT` (défaut 3000).
- **CORS** : autorisé pour le frontend (`FRONTEND_URL`, localhost).
- **Global** : pas de préfixe global ; validation `ValidationPipe`, filtre d’exceptions global.
- **Static** : `/uploads/` → dossier `uploads`.
- **Swagger** : `/api/docs` avec Bearer.

| **StudentsModule** | Self-service étudiant | Proforma, certificat, statut financier, reçus |

### 2.3 Dépendances importantes

## Workflows métier principaux

### Inscription étudiant

création Person  
→ création User  
→ inscription formation  
→ génération matricule  
→ activation étudiant

### Paiement

création paiement  
→ validation caissier  
→ génération reçu  
→ mise à jour statut financier

### Notes

enseignant saisit notes  
→ soumission  
→ validation chef département  
→ validation scolarité  
→ verrouillage

### Pointage enseignant

arrivée  
→ pointage  
→ validation comptable  
→ utilisé pour calcul paie

---

## Règles métier principales

### Inscription

- un étudiant ne peut avoir qu'une inscription active par année académique
- une inscription est liée à une formation et un groupe

### Paiement

- un paiement doit être validé par un caissier
- la validation génère un reçu
- le statut financier de l'étudiant est mis à jour

### Notes

- les notes doivent être validées avant d'être verrouillées
- aucune modification possible après validation finale

### Pointage

- un pointage doit être lié à une séance d'emploi du temps
- seuls les pointages validés peuvent être utilisés pour la paie

---

## Standards de qualité du code

### Backend

- architecture modulaire NestJS
- DTO + validation class-validator
- services métier séparés des controllers
- Prisma pour l'accès base de données

### Frontend

- utilisation du design system existant
- composants réutilisables
- gestion des états cohérente
- pas de logique métier côté UI

### Règles générales

- ne pas dupliquer la logique métier
- privilégier les services backend
- documenter les endpoints Swagger

## 3. Frontend (Next.js)

### 3.1 Routes principales

| Zone | Chemins | Rôle cible |
|------|---------|------------|

| **Comptable** | `/dashboard/comptable`, tarifs, paiements, recouvrement, pointages, paie, cloture, historique cloture, caisse, comptabilite, daf, taux-horaires | CAISSIER, CHEF_COMPTABLE, DAF |
| **Scolarité** | `/dashboard/scolarite`, formations, filières, campus, salles, enseignants, etudiants, classes, inscriptions, emploi-du-temps, personnel, transfert | SCOLARITE, ADMIN, SUPER_ADMIN |
| **Pédagogie** | `/dashboard/pedagogie`, classes | SERVICE_PEDAGOGIQUE, ADMIN, SUPER_ADMIN |
| **Enseignant** | `/dashboard/enseignant`, notes, pointage, emploi-du-temps, paie | TEACHER |
| **Étudiant** | `/dashboard/etudiant`, notes, emploi-du-temps, documents | STUDENT |
| **Chef de département** | `/dashboard/chef-departement` | DEPT_HEAD |
| **Auditeur** | `/dashboard/auditeur`, journal | AUDITOR |
| **Partagé** | `/dashboard/profil`, `/dashboard/notifications`, `/dashboard/rapports` | Selon droits |

### 3.2 Lib & composants

- **`lib/api.ts`** : `api<T>(path, options)`, `downloadFile`, `getApiUrl`, `getFetchUrl`.
- **`lib/session.ts`** : token + user (localStorage), `clearSession`, `isSessionValid`, `isTokenNotExpired`.
- **Contextes** : `ThemeContext` (thème / couleurs / favicon), `ToastContext` (succès/erreur/info).
- **Design system** (`components/ui`) : `PageHeader`, `Card`, `NavCard`, `Button`, `BadgeStatus`, `EmptyState`, `Spinner`, `DataTable` (tri optionnel), `Pagination`, `KpiCard`, `Label`, `Input`, `Select`, `Textarea`, `FormGroup`, **`Icon`** (jeu d’icônes SVG dans `icons.tsx`). Layout **uniforme** : `Sidebar`, `DashboardHeader`, `AppShell` (sidebar + header pour tous les dashboards ; config par pathname et rôle dans `config/sidebar.ts`). **Icônes** : toutes les entrées de la sidebar et toutes les NavCards des dashboards ont une icône ; EmptyState, KpiCard et boutons d’action (ex. Nouvelle inscription) utilisent aussi des icônes.

## 4. Ce qui existe vs ce qui reste à faire

D'après issa.txt et le code actuel.

### 4.1 Déjà en place (backend + frontend)

- Auth (login, JWT, redirection par rôle), structure académique (formations, maquettes, UE, EC, salles), campus, filières.
- Utilisateurs et personnes (étudiants, enseignants, personnel), génération matricules, lien User ↔ Person.
- Inscriptions (API complète, cohortes, statuts, clôture, bulk-assign), côté front (liste, formulaire, design system sur la page Inscriptions).
- Finances étudiants (tarifs, paiements, validation, statut en règle, recouvrement).
- Self-service étudiant (proforma, certificat, reçus, statut).
- Emploi du temps (courses + timetables), conflits, bulk.
- Notes (saisie, sessions, demandes de modification, approbation/rejet).
- Pointage (arrivée/départ, validation, mes cours du jour).
- Paie (preview, calcul, génération, bulletins), taux horaires.
- Vigilance (présence), Gouvernance (états financiers, brèche), Vigile (check-in).
- Audit (logs, export), Notifications (liste, count, lu), Rapports (effectifs, recettes, taux réussite, export).
- Apparence & thème (SUPER_ADMIN) : couleurs, logos, favicon, ThemeProvider.

### 4.2 À compléter ou renforcer

| Domaine | À faire |
|--------|---------|
| **Auth** | Guards @Roles() sur toutes les routes sensibles ; page **profil** (GET/me, PATCH /users/me, changement mot de passe). |
| **Inscriptions** | Règles métier explicites (enjambement, affectation unique) ; formulaire + contrôles temps réel ; cohérence liste par formation/cohorte. |
| **Notes** | Date limite de saisie configurable ; file de validation complète en UI (scolarité / chef de département) ; historique des modifications. |
| **Documents PDF** | Vérifier/coder génération reçu après validation paiement ; templates proforma/certificat ; boutons self-service clairs. |
| **Emploi du temps** | Clarifier ou unifier courses vs timetables ; **vue calendrier/semaine** ; conflits avant enregistrement ; vues enseignant/étudiant homogènes. |
| **Pointage** | Lier strictement à un cours (EDT) ; statuts VALIDE / NON_REMUNERE / REFUSE ; écran **liste pointages à valider** (comptable). |
| **Paie** | Confirmer cryptage bulletin (matricule) ; interface **calcul paie** (mois, liste, heures, montants) ; historique des paies. |
| **Gouvernance** | Notification Directeur (demande de brèche) ; blocage modification tant que brèche non traitée ; historique états + brèches en UI. |
| **Vigilance** | Mise à jour **temps réel** (polling 30 s ou WebSocket) ; pastilles vert/rouge ; filtres (département, type). |
| **Vigile** | Log des passages (CheckInLog) côté backend ; interface kiosque **plein écran** (vert/rouge, message refus, saisie manuelle). |
| **Audit** | Enregistrement **systématique** des actions sensibles (notes, finances, inscriptions, validations) ; optionnel : connexions/échecs. |
| **Notifications** | Typage des notifications côté backend ; envoi lors validations/brèche ; cloche + liste + marquer lu bien intégrés. |
| **Rapports** | Graphiques et vues synthèse ; exports PDF/Excel par rôle. |
| **Design** | Étendre le design system à toutes les pages critiques ; densité type ERP ; empty states, pagination, toasts partout. |

### 4.3 Priorisation pour une plateforme complète

1. **Sécurité** : Guards @Roles partout ; page profil + PATCH /users/me + changement de mot de passe.
2. **Inscriptions** : Règles métier + formulaire complet + listes/filtres.
3. **Notes** : Date limite + workflow de validation en UI + historique.
4. **Documents** : Génération PDF (reçu, proforma, certificat) + self-service étudiant.
5. **Emploi du temps** : Unification/clarification + vue calendrier/semaine.
6. **Pointage** : Lien EDT + statuts + écran validation (comptable).
7. **Paie** : Cryptage bulletin + UI calcul + historique.
8. **Gouvernance** : Notifications brèche + blocage + historique en UI.
9. **Vigilance** : Temps réel (polling/WebSocket) + pastilles + filtres.
10. **Vigile** : Log CheckInLog + interface kiosque plein écran.
11. **Audit** : Couverture complète des actions sensibles.
12. **Notifications** : Typage + envoi automatique + UI cloche/liste.
13. **Rapports** : Graphiques + exports par rôle.
14. **Livrable** : Tests (flux critiques), Swagger à jour, déploiement (Apache2, sauvegardes BDD).
